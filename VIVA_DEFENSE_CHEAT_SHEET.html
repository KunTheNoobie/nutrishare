Threat 1: Cross-Site Request Forgery (CSRF — OWASP A05 / CWE-352)

The Attack: A hacker creates an external website with a hidden form pointing to http://127.0.0.1:8000/donations. A logged-in donor's browser automatically attaches session cookies and submits spam food.
Why validation fails: Form validation checks data format (string/number). Since the hacker's form sends valid text, validation passes 100%! It cannot verify request origin.
NutriShare Defense: Synchronizer Token (donations/create.blade.php Line 18). @csrf generates a secret 256-bit token tied to session. Laravel's VerifyCsrfToken middleware blocks invalid tokens with HTTP 419 Page Expired.

Threat 1: Broken Access Control & Forced Browsing (OWASP A01 / CWE-285)

The Attack: A normal NGO user types /admin/verifications into their browser URL or sends a POST request to /admin/verifications/5/review with action=approved to approve their own organization.
Why validation fails: Form validation only checks that action=approved is a valid string. The data is valid, so validation passes! It cannot check whether the caller is an authorized admin.
NutriShare Defense: RBAC Middleware (app/Http/Middleware/CheckRole.php Line 15). We guard admin routes with role:admin,moderator. The middleware inspects $request->user()->role directly from the session, aborting unapproved users with HTTP 403 Forbidden. 

// app/Http/Middleware/CheckRole.php (Line 15)
public function handle(Request $request, Closure $next, ...$roles): Response {
    if (!$request->user() || !in_array($request->user()->role, $roles)) {
        abort(403, 'Unauthorized access.');
    }
    return $next($request);
}

Threat 2: OTP Brute-Force Account Takeover (OWASP A07 / CWE-307)

The Attack: Attacker requests a password reset for victim@nutrishare.org and uses a bot script to guess all 1,000,000 combinations (000000 to 999999) on POST /forgot-password/otp/verify.
Why validation fails: Form validation only checks otp: digits:6. Every guess is a 6-digit number, so validation allows infinite guesses!

3. Single-Use: The OTP is deleted immediately upon successful verification.

PROVIDE (WE EXPOSE THIS) POST /api/user/verify-ngo

Checks if an NGO has an approved account, valid government ROS license, and returns their peer trust rating.

Request: requestID (string), timestamp (ISO-8601 string), user_id (integer, exists:users,id)

// app/Http/Controllers/Api/UserVerificationApiController.php (Lines 40-85)
public function verifyNgo(Request $request): JsonResponse {
    try {
        $ifa = SecurityHelper::validateIfaRequest($request->all());

        $validated = $request->validate([
            'user_id' => 'required|integer|exists:users,id',
        ]);

        $user = User::find($validated['user_id']);

        if (!$user || $user->role !== 'ngo') {
            return response()->json(SecurityHelper::ifaResponse('F', [
                'requestID'   => $ifa['requestID'],
                'is_verified' => false,
                'reason'      => 'User is not registered as an NGO.',
            ]), 200);
        }

        $isVerified = $user->verification_status === 'approved';
        $hasValidLicense = VerificationDocument::where('user_id', $user->id)
            ->where('status', 'approved')
            ->whereIn('document_type', ['license', 'food_premise_license'])
            ->exists();

        return response()->json(SecurityHelper::ifaResponse('S', [
            'requestID'           => $ifa['requestID'],
            'is_verified'         => $isVerified && $hasValidLicense,
            'verification_status' => $user->verification_status,
            'trust_rating'        => $user->trust_rating ?? 5.0,
        ]), 200);
    } catch (\Exception $e) {
        return response()->json(SecurityHelper::ifaResponse('E', null, 'Failed to verify.'), 500);
    }
}

🎯 Design Pattern: State Pattern (GoF Behavioural)
🗣️ Look Tutor in the Eye & Say:
"The State Pattern allows an object to alter its behavior when its internal state changes. The object will appear to change its class."

Why not just use an Enum? (Tutor Trap): An Enum is only a static string label. But in surplus food logistics, each stage has different rules: in PendingState you can only approve or reject; in ApprovedState you cannot collect food unless a vehicle is assigned. If we used an Enum, we would have messy if-else ladders across controllers, violating the Open/Closed Principle. The State Pattern isolates each state's rules inside its own class. 

// 1. Context Model delegates to State: app/Models/Claim.php (Line 93)
namespace App\Models;
use App\States\Claim\{ClaimState, PendingState, ApprovedState, CollectedState};

class Claim extends Model {
    public function getStateObject(): ClaimState {
        return match ($this->status) {
            'approved'  => new ApprovedState($this),
            'collected' => new CollectedState($this),
            default     => new PendingState($this),
        };
    }
}

// 2. PendingState blocks premature collection: app/States/Claim/PendingState.php (Line 21)
namespace App\States\Claim;

class PendingState extends ClaimState {
    public function getStateName(): string { return 'pending'; }

    public function allowedActions(): array {
        return ['approve', 'reject', 'cancel']; // 'collect' is blocked here!
    }

    public function canPerform(string $action): bool {
        return in_array(strtolower($action), $this->allowedActions());
    }
}

class EmailStrategy implements NotificationStrategyInterface {
    public function send(User $recipient, string $subject, string $message): bool {
        Mail::raw($message, function ($mail) use ($recipient, $subject) {
            $mail->to($recipient->email)->subject("[NutriShare] {$subject}");
        });

// 3. Context Dispatcher: app/Strategies/Notification/NotificationDispatcher.php (Lines 45-65)
namespace App\Strategies\Notification;
use App\Models\User;

class NotificationDispatcher {
    public function resolveStrategy(string $channel): NotificationStrategyInterface {
        return match (strtolower($channel)) {
            'sms'   => new SmsStrategy(),
            'email' => new EmailStrategy(),
            default => new EmailStrategy(),
        };
    }

    public function dispatch(User $recipient, string $subject, string $message, ?string $channel = null): bool {
        $selectedChannel = $channel ?? $recipient->notification_preference ?? 'email';
        $strategy = $this->resolveStrategy($selectedChannel);
        return $strategy->send($recipient, $subject, $message);
    }
}

❓ Tough Tutor Questions (Easy to Understand Answers):
Q1: Why did you use Strategy instead of Observer or State pattern?
Answer: "Observer broadcasts events to multiple listeners simultaneously; State changes internal object behavior based on state lifecycle transitions. Strategy is specifically used to swap algorithms or service providers (like Email vs SMS communication gateways) dynamically without modifying the caller."
Q2: Can an attacker forge a signed URL if they know the donation ID?
Answer: "No! Signed URLs use HMAC-SHA256 keyed with Laravel's secret APP_KEY stored only on our server. Unless the attacker steals the APP_KEY from our .env file, they cannot generate a valid signature hash."
Q3: What if an attacker sends %0d%0a (URL-encoded CRLF) in the note field?
Answer: "Laravel's HTTP request pipeline automatically URL-decodes query and body parameters before passing them to the application. When our Eloquent mutator runs, the characters are already literal bytes and are stripped by the regex."
Q4: What if an SMS gateway fails during critical alert dispatch?
Answer: "The NotificationDispatcher implements a graceful fallback: if SMS dispatch returns false or throws an exception, it falls back to EmailStrategy and writes an emergency error entry to SystemLog."
