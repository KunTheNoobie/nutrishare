🎯 Section A: Design Pattern — Observer Pattern (GoF Behavioural)

🗣️ Look Tutor in the Eye & Say:
"The Observer Pattern is a GoF behavioural design pattern that defines a one-to-many dependency between objects. When the subject undergoes a state change, all its registered observers are automatically notified and updated without the subject having tight coupling to their concrete implementations."

Why in Module 1: Publishing surplus food triggers multiple asynchronous side-effects: dispatching audit logs, sending push alerts to registered NGOs, and clearing cached catalogues. Embedding these notifications directly inside DonationController violates the Single Responsibility Principle (SRP) and Open/Closed Principle (OCP). The Observer hooks into Eloquent lifecycle events directly, ensuring notifications trigger consistently whether records are created via the web UI, database seeders, or API endpoints.

{

        // Validate standard IFA envelope headers

            ->active() // Scope: available and non-expired

public function verifyNgoBeforeClaim(int $ngoUserId): bool
{
    try {
        $response = Http::timeout(5)->post(config('app.url').'/api/user/verify-ngo', [
            'requestID' => uniqid('VERIFY-'),
            'timestamp' => now()->toIso8601String(),
            'user_id'   => $ngoUserId,

        if ($response->successful() && $response->json('status') === 'S') {
            return (bool) ($response->json('data.is_verified') ?? false);
        }
        return false; // Fail-closed on error
    } catch (\Exception $e) {
        \Log::error("Web service failure in verifyNgoBeforeClaim: {$e->getMessage()}");
        return false; // Fail-closed: block claim if verification service is down
    }
}

❓ Section D: Tough Tutor Viva Questions & Model Defenses

Q1: Why not just dispatch the notification email inside DonationController@store?
Answer: "Placing notification logic inside the controller violates the Single Responsibility Principle. If donations are inserted via database seeders, artisan import commands, or external REST APIs, the controller would be bypassed and notifications would fail. The Observer hooks directly into the Eloquent model lifecycle, ensuring consistent execution across all entry points while keeping the controller lightweight."
Q2: What happens if the Mail server (Mailpit) is offline when a donation is created? Does the database transaction roll back?
Answer: "No, tutor! The database transaction commits immediately. The Observer dispatches SendDonationNotificationJob to Laravel's asynchronous database queue worker. The HTTP client receives an immediate 200/302 success response, while the queue worker handles retries with exponential backoff independently, preventing mail server latency from impacting donor UX."
Q3: How does the Observer Pattern in your module differ from the Publish-Subscribe pattern?
Answer: "In the classic GoF Observer Pattern, the subject maintains a direct registry of its observers. In Pub-Sub, an intermediary message broker or event bus decouples the publisher entirely from subscribers. In our Laravel implementation, the Eloquent model acts as the Subject, and Laravel's Event Dispatcher acts as the channel delegating to DonationObserver."
Q4: Can an attacker bypass CSRF protection by submitting an AJAX request with custom headers?
Answer: "No. Due to Same-Origin Policy (SOP), an attacker on an external malicious origin cannot read or attach our custom X-CSRF-TOKEN header without CORS explicitly allowing it. Laravel's VerifyCsrfToken middleware inspects both the POST body _token and the X-CSRF-TOKEN header, rejecting any unauthenticated cross-origin request."

🎯 Section A: Design Pattern — Factory Method Pattern (GoF Creational)

🗣️ Look Tutor in the Eye & Say:
"The Factory Method Pattern is a GoF creational pattern that defines an interface or abstract class for creating an object, but lets subclasses decide which concrete class to instantiate. It defers the instantiation logic to subclasses."

Why in Module 2: Different user personas have radically different business workflows upon registration. Adding new personas (e.g. logistics volunteers) requires only adding a new creator class.

abstract class UserCreator {

public function verifyNgo(Request $request): JsonResponse
{
    try {
        // Validate IFA request headers
        $ifa = SecurityHelper::validateIfaRequest($request->all());

        $validated = $request->validate([
            'user_id' => 'required|integer|exists:users,id',
        ]);

        $user = User::find($validated['user_id']);

        if (!$user || $user->role !== 'ngo') {
            return response()->json(
                SecurityHelper::ifaResponse('F', [
                    'requestID'   => $ifa['requestID'],
                    'is_verified' => false,
                    'reason'      => 'User is not registered as an NGO.',
                ]),
                200
            );
        }

        $isVerified = $user->verification_status === 'approved';
        $hasValidLicense = VerificationDocument::where('user_id', $user->id)
            ->where('status', 'approved')
            ->whereIn('document_type', ['license', 'food_premise_license'])
            ->exists();

        return response()->json(
            SecurityHelper::ifaResponse('S', [
                'requestID'           => $ifa['requestID'],
                'is_verified'         => $isVerified && $hasValidLicense,
                'verification_status' => $user->verification_status,
                'has_valid_license'   => $hasValidLicense,
                'organization_name'   => $user->organization_name,
                'trust_rating'        => $user->averageRating(),
            ]),
            200
        );
    } catch (\Illuminate\Validation\ValidationException $e) {
        return response()->json(
            SecurityHelper::ifaResponse('F', null, 'Validation error: ' . $e->getMessage()),
            422
        );
    } catch (\Exception $e) {
        return response()->json(
            SecurityHelper::ifaResponse('E', null, 'Internal server error.'),
            500
        );
    }
}

🗣️ Look Tutor in the Eye & Say:
"The Strategy Pattern is a GoF behavioural design pattern that defines a family of algorithms, encapsulates each one into a separate class, and makes them interchangeable. It lets the algorithm vary independently from clients that use it."

Why in Module 4: Warehouse facility management requires dynamic alert delivery channels. Low-priority notices (routine food intake confirmations) are delivered via low-cost SMTP Email. Hardcoding communication APIs directly into InventoryController creates rigid coupling to specific mailers or SMS SDKs. The Strategy Pattern decouples notification generation from transport mechanisms.

class EmailStrategy implements NotificationStrategyInterface {
    public function send(User $recipient, string $subject, string $message): bool {
        Mail::raw($message, function ($mail) use ($recipient, $subject) {
            $mail->to($recipient->email)->subject("[NutriShare] {$subject}");
        });
        return true;

namespace App\Strategies\Notification;
use App\Models\User;

class NotificationDispatcher {
    public function resolveStrategy(string $channel): NotificationStrategyInterface {
        return match (strtolower($channel)) {
            'sms'   => new SmsStrategy(),
            'email' => new EmailStrategy(),
            default => new EmailStrategy(),
        };
    }

    public function dispatch(User $recipient, string $subject, string $message, ?string $channel = null): bool {
        $selectedChannel = $channel ?? $recipient->notification_preference ?? 'email';
        $strategy = $this->resolveStrategy($selectedChannel);
        return $strategy->send($recipient, $subject, $message);
    }
}

❓ Section D: Tough Tutor Viva Questions & Model Defenses

Q1: What is the fundamental architectural difference between Strategy Pattern and Observer Pattern?
Answer: "The Observer Pattern is a one-to-many publish-subscribe mechanism where a subject broadcasts state change events to multiple unknown, decoupled observers. The Strategy Pattern is a one-to-one interchangeable algorithm mechanism where a context selectively executes exactly one encapsulated delivery algorithm (e.g. EmailStrategy vs SmsStrategy) at a time."
Q2: What prevents an attacker from replaying an expired HMAC signed URL next week?
Answer: "When generated with URL::temporarySignedRoute(), an expires UNIX timestamp is concatenated into the URL query string before generating the HMAC SHA-256 hash. Laravel's ValidateSignature middleware first verifies the cryptographic hash against APP_KEY, and then validates that now()->timestamp <= expires. If expired, access is aborted with HTTP 403 Invalid Signature."
Q3: Why sanitize CRLF in an Eloquent mutator instead of doing it in the view?
Answer: "Sanitizing in the view only protects web browser rendering. Audit logs are consumed by system administrators, SIEM security pipelines, terminal logs, and external audit tools. Sanitizing at the model mutator level guarantees that CRLF injection is eliminated at the point of persistence, safeguarding all log consumers."
Q4: Why not just use conditional if-else statements inside InventoryController for sending Email or SMS?
Answer: "Using procedural if ($channel == 'email') ... else if ($channel == 'sms') directly inside the controller tightly couples the controller to concrete vendor SDKs (e.g. AWS SNS, Twilio, Mailgun). If delivery algorithms change or push notifications are added, the controller must be modified and retested, violating the Open/Closed Principle. The Strategy Pattern isolates each delivery algorithm into its own testable class."
