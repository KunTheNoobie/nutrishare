2. Design Pattern
Observer Pattern (GoF Behavioural)
🗣️ Say This Out Loud (General Theory — Do NOT read notes):
"The Observer Pattern defines a one-to-many dependency between objects so that when one object (the Subject) changes state, all its registered dependents (the Observers) are automatically notified and updated. In enterprise web development, it decouples the core domain transaction from secondary side-effects like sending emails, telemetry logging, and push alerts."

Why & Where in Module 1: Without the Observer pattern, DonationController@store would become bloated with user querying, email compilation, and notification channels (violating Single Responsibility). We decouple it so the donor gets an instant HTTP response while SendDonationNotificationJob runs asynchronously via Laravel background queues (ShouldQueue).

UML Roles & Architecture:
• Subject (Observable): Donation model (app/Models/Donation.php) dispatches lifecycle events (created, updated).
• Observer Contract: DonationObserverInterface (app/Contracts/DonationObserverInterface.php:12-20) declares onDonationCreated and onDonationStatusChanged.
• Concrete Observer: DonationObserver (app/Observers/DonationObserver.php:15-64) listens to Eloquent model events.
• Async Queue Worker: SendDonationNotificationJob (app/Jobs/SendDonationNotificationJob.php:25-58) notifies verified NGOs.

app/Observers/DonationObserver.php Lines 15–35 (Concrete Observer) 
class DonationObserver implements DonationObserverInterface
{
    public function created(Donation $donation): void
    {
        $this->onDonationCreated($donation);
    }

    public function onDonationCreated(Donation $donation): void
    {
        // Non-blocking async queue dispatch: instant sub-second response for donor
        SendDonationNotificationJob::dispatch($donation);
    }
}

Threat 1: Cross-Site Request Forgery (CSRF — OWASP Top 10)

Attack Description: An attacker embeds a hidden script on an external malicious site (e.g., <form action="http://nutrishare.com/donations" method="POST">). When an authenticated donor visits that page, the browser automatically attaches NutriShare session cookies, silently creating fraudulent listings without the donor's consent.

Secure Coding Defense: Synchronizer Token Pattern (@csrf Directive)
Every state-modifying form embeds a cryptographically secure 256-bit token uniquely bound to the active session. Laravel's VerifyCsrfToken middleware intercepts incoming POST requests and compares the token. External forged requests lack this token and are terminated immediately with HTTP 419 Page Expired.

Threat 2: Stored Cross-Site Scripting (Stored XSS — OWASP Top 10 A03:2021 Injection)

Attack Description: An adversary injects malicious executable JavaScript inside donation input fields like title, description, or pickup_address (e.g. <script>alert(document.cookie)</script>). Secure Coding Defense: Context-Aware HTML Entity Escaping (Blade Sanitisation)

2. Design Pattern
Factory Method Pattern (GoF Creational)
🗣️ Say This Out Loud (General Theory — Do NOT read notes):
"The Factory Method Pattern defines an interface or abstract class for creating an object, but allows subclasses to decide which class to instantiate. It delegates instantiation logic to specialized creators, decoupling client callers from concrete classes and encapsulating business validation and initial state setup."

Why & Where in Module 2: Without the Factory Method, AuthController@register would contain fragile switch-case ladders for different roles. Commercial donors can be approved immediately, but NGOs must strictly be initialized with verification_status = 'pending', audit logs, and admin notifications. {

Threat 2: OTP Brute-Force & Account Takeover (OWASP Top 10 A07:2021)

Attack Description: Password recovery mechanisms using 6-digit numeric OTPs have a search space of only 1,000,000 possibilities. Without throttling, an attacker floods POST /forgot-password/otp/verify with automated scripts, guessing the token within minutes to seize control of user accounts.

Secure Coding Defense: Cryptographic Token Invalidation, Sliding Expiry & Throttling
1) Old OTPs are deleted before issuing new ones to eliminate replay attacks.
2) Generated via cryptographically secure random_int(0, 999999) with a strict 10-minute expiry (now()->addMinutes(10)).
3) Routes enforce rate limiting via middleware('throttle:6,1') (max 6 attempts per minute per IP address).

"The State Pattern allows an object to alter its behavior when its internal state changes, appearing as if the object changed its class. It encapsulates state-specific behaviors inside dedicated state classes and eliminates conditional if-else or switch statements."

class ApprovedState extends ClaimState

    {

public function view(User $user, Claim $claim): bool
{
    if ($user->isAdmin() || $user->isModerator()) return true;
    if ($user->isNgo())   return $claim->user_id === $user->id;
    if ($user->isDonor()) return $claim->donation->user_id === $user->id;

Threat 2: State Manipulation & Race Conditions (OWASP Top 10 A04:2021 Insecure Design)

Attack Description: Attackers submit injected JSON payloads like {"status": "collected"} directly to endpoints, or send rapid concurrent requests to approve and collect the same claim simultaneously, creating double-allocation race conditions.

Secure Coding Defense: Database Transactions with Pessimistic Row Locking
All state transitions execute inside DB::transaction(...) using Claim::where('id', $claim->id)->lockForUpdate()->firstOrFail(). The row is locked at the database engine level until the transaction commits, completely preventing race conditions and unauthorized state transitions.

app/Http/Controllers/ClaimController.php Lines 131–141 (Pessimistic Row Locking) 
return DB::transaction(function () use ($claim, $action) {
    // Pessimistic row locking prevents concurrent race condition tampering
    $lockedClaim = Claim::where('id', $claim->id)->lockForUpdate()->firstOrFail();
    $success = $lockedClaim->transitionTo($action);
    if ($success) {
        return redirect()->route('claims.show', $lockedClaim)
            ->with('success', "Claim {$action}d successfully.");
    }
    return redirect()->route('claims.show', $lockedClaim)
        ->with('error', "Cannot {$action} this claim in its current state.");
});

2. Design Pattern
Strategy Pattern (GoF Behavioural)
🗣️ Say This Out Loud (General Theory — Do NOT read notes):
"The Strategy Pattern defines a family of algorithms, encapsulates each one into a dedicated class, and makes them interchangeable at runtime. It lets the algorithm vary independently from the clients that use it, eliminating brittle if-else ladders and ensuring high cohesion."

Why & Where in Module 4: After a food item is added to inventory, the system dispatches a confirmation alert. The Strategy Pattern swaps the notification channel dynamically at runtime based on the user's preference (notification_preference) or alert urgency—using EmailStrategy for standard emails or SMSStrategy for urgent telephony alerts, without changing controller code.

UML Roles & Architecture:
• Strategy Interface: NotificationStrategyInterface (app/Strategies/Notification/NotificationStrategyInterface.php:14-24) declares send() and getChannelName().
• Concrete Strategies: EmailStrategy (app/Strategies/Notification/EmailStrategy.php:14-34) and SMSStrategy (app/Strategies/Notification/SMSStrategy.php:14-34).
• Context / Dispatcher: NotificationDispatcher (app/Strategies/Notification/NotificationDispatcher.php:12-42) resolves strategy based on user preference.
• Client: InventoryController@addFoodItem (app/Http/Controllers/InventoryController.php:134-142) triggers delivery via the dispatcher.

app/Strategies/Notification/NotificationDispatcher.php Lines 12–42 (Strategy Context / Dispatcher) 
class NotificationDispatcher
{
    public function dispatch(User $user, string $subject, string $message): bool
    {
        // Dynamic runtime strategy resolution
        $strategy = $this->resolveStrategy($user->notification_preference ?? 'email');
        $recipient = $this->getRecipient($user, $strategy);
        return $strategy->send($recipient, $subject, $message);
    }
}
3. Software Security
2 Specific Threats & Secure Coding Defenses (From Report)

Threat 1: Log Injection / CRLF Injection (OWASP Top 10 A09:2021 Logging Failures)

Attack Description: Untrusted user input written directly to system logs allows attackers to inject Carriage Return (\r) and Line Feed (\n) sequences (e.g. Coldroom\r\n[2026-09-06] ADMIN: Granted Superuser...), forging statutory audit entries or concealing unauthorized actions.

Secure Coding Defense: Server-Side CRLF Sanitisation via Mutators & SecurityHelper
SecurityHelper::sanitizeLogInput() strips all \r, \n, and ASCII control characters (0–31). To make bypass impossible, SystemLog Eloquent mutators (setDescriptionAttribute and setActionAttribute) automatically sanitize every log entry prior to database storage.

app/Models/SystemLog.php & app/Helpers/SecurityHelper.php Lines 47–62 (CRLF Sanitisation Mutators) 
// app/Helpers/SecurityHelper.php: Lines 14-35
public static function sanitizeLogInput(string $input): string
{
    $sanitized = str_replace(["\r\n", "\r", "\n"], ' ', $input);
    return trim(preg_replace('/[\x00-\x08\x0B\x0C\x0E-\x1F\x7F]/', '', $sanitized));
}

// app/Models/SystemLog.php: Lines 47-54 (Eloquent Model Mutator)
public function setDescriptionAttribute(string $value): void
{
    $this->attributes['description'] = SecurityHelper::sanitizeLogInput($value);
}

Threat 2: Parameter Tampering & IDOR on Action URLs (OWASP Top 10 A01/A04)

Attack Description: In quick-claim action URLs (e.g. /inventory/quick-claim/4?user=5), an adversary alters the query string parameters from donation #4 to donation #7 or changes the user ID to hijack high-value supplies or bypass allocation limits.

Secure Coding Defense: Cryptographic HMAC URL Signing (URL::signedRoute)
All quick-action links are cryptographically signed using HMAC SHA-256 bound to the application's secret key. The route enforces Laravel's signed middleware. Any modification to parameters invalidates the HMAC signature and aborts with an HTTP 403 Forbidden.

public function checkSafety(Request $request): JsonResponse
{
    $ifa = SecurityHelper::validateIfaRequest($request->all());
    $item = FoodItem::with(['category', 'allergenTags'])->find($request->food_item_id);

    $isExpired = $item->expiry_date ? $item->expiry_date->isPast() : false;
    $isSafe = !$isExpired;

    return response()->json(SecurityHelper::ifaResponse('S', [
        'requestID' => $ifa['requestID'],
        'food_item' => [
            'id'            => $item->id,
            'name'          => $item->name,
            'allergens'     => $item->allergenTags->pluck('name'),
            'expiry_date'   => $item->expiry_date?->toIso8601String(),
            'safety_status' => $isSafe ? 'SAFE' : 'EXPIRED / AT RISK',
        ]
    ]), 200);
}

public function fetchActiveDonationsForWarehouse(): array
{
    $response = Http::timeout(10)->get(config('app.url') . '/api/donations/active', [
        'requestID' => uniqid('INV-PREVIEW-'),
        'timestamp' => now()->toIso8601String(),
    ]);

    if ($response->successful()) {
        $data = $response->json();
        return $data['status'] === 'S' ? ($data['data']['donations'] ?? []) : [];
    }
    return [];
}
