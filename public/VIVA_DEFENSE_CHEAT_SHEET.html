2. Design Pattern
Observer Pattern (GoF Behavioural)
🗣️ Say This Out Loud (General Theory — Do NOT read notes):
"The Observer Pattern defines a one-to-many link between objects. When the main object (the Subject) changes state, all registered Observers get notified automatically. This separates the main job (saving the donation) from background tasks like sending emails and alerts."

Why & Where in Module 1: Without the Observer pattern, DonationController would become messy because it would have to find NGOs, build emails, and send alerts directly. With Observer, the donor gets an instant response, and SendDonationNotificationJob handles the notifications in the background.

UML Roles & Architecture:
• Subject (Observable): Donation model (app/Models/Donation.php) triggers events when created or updated.
• Observer Interface: DonationObserverInterface (app/Contracts/DonationObserverInterface.php:12-20) defines onDonationCreated and onDonationStatusChanged.
• Concrete Observer: DonationObserver (app/Observers/DonationObserver.php:15-35) listens for new donations.
• Background Queue Worker: SendDonationNotificationJob (app/Jobs/SendDonationNotificationJob.php:25-58) sends notifications to verified NGOs.

app/Observers/DonationObserver.php Lines 15–35 (Concrete Observer) 
class DonationObserver implements DonationObserverInterface
{
    public function created(Donation $donation): void
    {
        $this->onDonationCreated($donation);
    }

    public function onDonationCreated(Donation $donation): void
    {
        // Runs in background queue so donor gets instant response
        SendDonationNotificationJob::dispatch($donation);
    }
}

Threat 1: Cross-Site Request Forgery (CSRF)

What is the attack? A fake external website tricks a logged-in donor's browser into secretly submitting a form, creating fake donations without the donor knowing.

How we fix it? Synchronizer Token (@csrf)
We add @csrf inside the form. Laravel creates a secret 256-bit token for the session. When the form submits, Laravel checks this token. If the token is missing or altered, Laravel blocks it with 419 Page Expired.

<form method="POST" action="{{ route('donations.store') }}" enctype="multipart/form-data">
    {{-- CSRF Token: Protects against forged external requests --}}
    @csrf
    ...
</form>

Threat 2: Stored Cross-Site Scripting (Stored XSS)

What is the attack? A hacker enters malicious JavaScript like <script>alert('XSS')</script> into the donation title or description. If displayed without cleaning, the script runs in the browser of any user who opens the page.

How we fix it? Automatic HTML Escaping
In Blade views, we print variables using {{ $donation->title }}. Blade automatically runs PHP's htmlspecialchars(), converting < into &lt; and > into &gt; so it renders as safe plain text instead of executing.

2. Design Pattern
Factory Method Pattern (GoF Creational)
🗣️ Say This Out Loud (General Theory — Do NOT read notes):
"The Factory Method Pattern gives us an interface or abstract class for creating objects, but lets subclasses decide which exact class to create. It moves the setup and creation code into separate creator classes, so the registration controller stays simple."

Why & Where in Module 2: Commercial donors can be approved immediately when they sign up, but NGOs must start with verification_status = 'pending' until an admin checks their documents. • Product: User model.
• Client: AuthController@register (app/Http/Controllers/AuthController.php:98-112) calls UserCreator::resolve($role)->createUser($data).

Threat 1: Broken Access Control & Privilege Escalation

What is the attack? A regular donor or unverified NGO tries to type the admin URL /verification directly into their browser bar to see the admin queue and approve themselves.

How we fix it? Role Middleware (CheckRole)
All admin routes are wrapped in CheckRole middleware requiring role:admin,moderator. In addition, ReviewVerificationDocumentRequest has an authorize() check. If a non-admin tries to enter, Laravel blocks them with 403 Forbidden.

app/Http/Middleware/CheckRole.php Lines 14–22 (RBAC Middleware) 
public function handle(Request $request, Closure $next, ...$roles)
{
    if (!$request->user() || !in_array($request->user()->role, $roles)) {
        abort(403, 'Unauthorized. You do not have the required role to access this resource.');
    }
    return $next($request);
}

Threat 2: OTP Brute-Force & Account Takeover

What is the attack? An attacker uses an automated bot to guess the 6-digit password reset OTP by testing thousands of numbers per second.

How we fix it? Expiry Windows & Rate Limiting (throttle:6,1)
We generate random 6-digit OTPs that expire in 10 minutes and delete old ones. In routes/web.php, we apply middleware('throttle:6,1'). This restricts guessing to 6 tries per minute.

public function verifyNgo(Request $request): JsonResponse
{
    $ifa = SecurityHelper::validateIfaRequest($request->all());
    $user = User::find($request->user_id);

    $isVerified = ($user && $user->verification_status === 'approved');
    $hasValidLicense = VerificationDocument::where('user_id', $user?->id)
        ->where('status', 'approved')
        ->whereIn('document_type', ['license', 'food_premise_license'])
        ->exists();

    return response()->json(SecurityHelper::ifaResponse('S', [
        'requestID'           => $ifa['requestID'],
        'is_verified'         => ($isVerified && $hasValidLicense),
        'verification_status' => $user?->verification_status,
        'trust_rating'        => $user?->averageRating(),
    ]), 200);
}

class ApprovedState extends ClaimState

    {

        return true;
    }
}

Threat 1: Broken Object Level Authorization (BOLA / IDOR)

What is the attack? An NGO user changes the URL from /claims/12 to /claims/14 to see or change another charity's driver and vehicle details.

How we fix it? Policy Authorization (ClaimPolicy)
Every controller method calls $this->authorize('view', $claim). The policy checks if you are an admin, the claiming NGO ($claim->user_id === $user->id), or the owning donor. If not, Laravel blocks access with 403 Forbidden.

app/Policies/ClaimPolicy.php Lines 33–40 (Policy IDOR Gate) 
public function view(User $user, Claim $claim): bool
{
    if ($user->isAdmin() || $user->isModerator()) return true;
    if ($user->isNgo())   return $claim->user_id === $user->id;
    if ($user->isDonor()) return $claim->donation->user_id === $user->id;
    return false;
}

Threat 2: State Manipulation & Race Conditions

What is the attack? An attacker skips steps by sending a fake status: collected request directly, or two users try to approve/collect the same claim at the exact same split-second.

How we fix it? Database Row Locking (lockForUpdate)
All status changes run inside DB::transaction(...) using Claim::where('id', $claim->id)->lockForUpdate(). This locks the database row until the update finishes, preventing race conditions and keeping data clean.

app/Http/Controllers/ClaimController.php Lines 131–141 (Pessimistic Row Locking) 
return DB::transaction(function () use ($claim, $action) {
    // Locks the database row so no one else can modify it simultaneously
    $lockedClaim = Claim::where('id', $claim->id)->lockForUpdate()->firstOrFail();
    $success = $lockedClaim->transitionTo($action);
    if ($success) {
        return redirect()->route('claims.show', $lockedClaim)
            ->with('success', "Claim {$action}d successfully.");
    }
    return redirect()->route('claims.show', $lockedClaim)
        ->with('error', "Cannot {$action} this claim in its current state.");
});

2. Design Pattern
Strategy Pattern (GoF Behavioural)
🗣️ Say This Out Loud (General Theory — Do NOT read notes):
"The Strategy Pattern defines a set of algorithms, puts each one into its own class, and makes them interchangeable at runtime. It lets the sending method change independently from the controllers that use it, getting rid of messy if-else blocks."

Why & Where in Module 4: When food is added to inventory, the system sends an alert. The Strategy Pattern picks the right delivery channel at runtime (using EmailStrategy for emails or SMSStrategy for SMS) based on user preference, without changing the inventory controller code.

UML Roles & Architecture:
• Strategy Interface: NotificationStrategyInterface (app/Strategies/Notification/NotificationStrategyInterface.php:14-24) defines send() and getChannelName().
• Concrete Strategies: EmailStrategy (app/Strategies/Notification/EmailStrategy.php:14-34) and SMSStrategy (app/Strategies/Notification/SMSStrategy.php:14-34).
• Context / Dispatcher: NotificationDispatcher (app/Strategies/Notification/NotificationDispatcher.php:12-42) selects the strategy.
• Client: InventoryController@addFoodItem (app/Http/Controllers/InventoryController.php:134-142) calls the dispatcher.

app/Strategies/Notification/NotificationDispatcher.php Lines 12–42 (Strategy Context / Dispatcher) 
class NotificationDispatcher
{
    public function dispatch(User $user, string $subject, string $message): bool
    {
        // Picks email or sms strategy dynamically at runtime
        $strategy = $this->resolveStrategy($user->notification_preference ?? 'email');
        $recipient = $this->getRecipient($user, $strategy);
        return $strategy->send($recipient, $subject, $message);
    }
}

Threat 1: Log Injection / CRLF Injection

What is the attack? An attacker types Enter keys (\r\n) into a facility name, like Coldroom\r\n[ALERT] Superuser granted. When saved to logs, it creates a fake extra line that confuses admins during audits.

How we fix it? CRLF Sanitization in Mutators
In app/Helpers/SecurityHelper.php:14-35 and app/Models/SystemLog.php:47-62, our mutator strips all \r and \n characters before saving to the database, flattening the input into a single safe line.

app/Models/SystemLog.php & app/Helpers/SecurityHelper.php Lines 47–62 (CRLF Sanitisation Mutators) 
// app/Helpers/SecurityHelper.php: Strips Enter keys
public static function sanitizeLogInput(string $input): string
{
    $sanitized = str_replace(["\r\n", "\r", "\n"], ' ', $input);
    return trim(preg_replace('/[\x00-\x08\x0B\x0C\x0E-\x1F\x7F]/', '', $sanitized));
}

// app/Models/SystemLog.php: Mutator cleans description automatically
public function setDescriptionAttribute(string $value): void
{
    $this->attributes['description'] = SecurityHelper::sanitizeLogInput($value);
}

Threat 2: Parameter Tampering on Action Links

What is the attack? If we send a quick-claim link like /inventory/quick-claim/1?user=2, an attacker changes quick-claim/1 to quick-claim/2 in their URL bar to steal someone else's food allocation.

How we fix it? Cryptographic Signed URLs (URL::signedRoute)
We sign the URL with an HMAC hash using our secret key. If anyone alters the URL parameters, the digital signature breaks, and Laravel immediately rejects it with 403 Invalid Signature.

    'user'     => Auth::id(),
]);

    ->name('inventory.quick-claim')
