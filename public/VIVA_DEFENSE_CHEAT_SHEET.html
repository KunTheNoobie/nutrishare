🏗️ 2. Design Pattern: Observer app/Observers/DonationObserver.php:30
❓ Tutor Question: "Why did you use Observer pattern and how does it work?"
"We use the Observer Pattern to decouple donation creation from notification alerts. Donation is the Subject; DonationObserver is the Observer."
💬 Say This (Super Simple):
• How it works: When Donation::create() executes, Laravel automatically triggers DonationObserver::created().
• The observer dispatches SendDonationNotificationJob to create alerts for the donor and verified NGOs.
• Why use it: Complete separation of concerns. If tomorrow we add WhatsApp or push notifications, we never touch the Donation model code! 
// app/Observers/DonationObserver.php
public function onDonationCreated(Donation $donation): void {
    // Observer dispatches background notification job
    SendDonationNotificationJob::dispatch($donation);
}
🛡️ 3. Security: Mass Assignment & BOLA Requests/StoreDonationRequest.php:25
❓ Tutor Question: "What security threat could happen and how do you stop it?"
"Attackers attempt Mass Assignment (injecting status=claimed) or Broken Object Authorization (tampering with another donor's donation ID)."
💬 Say This (Super Simple):
• Defense 1 (Mass Assignment): We use Form Request validation (StoreDonationRequest) and model $fillable. Any unlisted fields sent by hackers are stripped out immediately.
• Defense 2 (BOLA / IDOR): We enforce DonationPolicy on update/delete. If $user->id !== $donation->user_id, Laravel returns an immediate 403 Forbidden! 
// app/Policies/DonationPolicy.php
public function update(User $user, Donation $donation): bool {
    return $user->id === $donation->user_id; // 403 Forbidden if not owner
}

🏗️ 2. Design Pattern: Factory Method Services/UserFactory/UserCreator.php:15
❓ Tutor Question: "Why did you use Factory Method and how does it work?"
"Instead of messy if/else statements during user registration, we use the Factory Method to instantiate specific user roles with their own onboarding policies."
💬 Say This (Super Simple):
• UserCreator is the abstract Creator. Subclasses NgoCreator and DonorCreator instantiate the user.
• How it works: When an NGO registers, NgoCreator automatically sets verification_status = 'pending' and triggers document upload workflows.
• When a Donor registers, DonorCreator sets verification_status = 'approved' immediately so they can donate right away! 
// app/Services/UserFactory/NgoCreator.php
class NgoCreator extends UserCreator {
    protected function makeUser(array $data): User {
        $data['role'] = 'ngo';
        $data['verification_status'] = 'pending'; // Requires admin audit
        return User::create($data);
    }
}
🛡️ 3. Security: Malicious File Upload & RCE VerificationController.php:35
❓ Tutor Question: "What security threat could happen and how do you stop it?"
"A malicious user tries to upload a .php web shell script disguised as a PDF certificate to achieve Remote Code Execution (RCE) on our server."
💬 Say This (Super Simple):
• MIME Validation: We enforce strict MIME whitelist (mimes:pdf,jpg,png|max:5120). PHP/executable files are immediately rejected.
• Cryptographic Hashing: Files are renamed to random SHA-256 hashes so original filenames cannot be exploited.
• Private Storage: Documents are stored in Storage::disk('private') outside the public web root, completely preventing direct browser execution! 
// app/Http/Controllers/VerificationController.php
$request->validate([
    'document' => 'required|file|mimes:pdf,jpg,png|max:5120',
]);
$path = $request->file('document')->store('verification_docs', 'private');

🏗️ 2. Design Pattern: State Pattern States/Claim/ClaimState.php:18
❓ Tutor Question: "Why did you use State pattern and how does it work?"
"Claims transition through strict stages: Pending ➔ Approved ➔ Collected. Each status is its own class instead of messy switch/case code."
💬 Say This (Super Simple):
• ClaimState is the abstract state. Concrete states are PendingState, ApprovedState, and CollectedState.
• How it works: Actions change depending on status. In PendingState, you can only approve() or reject().
• Why use it: Prevents illegal transitions! You cannot call collect() on a pending claim—the state class blocks it automatically! 
// app/States/Claim/PendingState.php
public function approve(): void {
    $this->claim->status = 'approved';
    $this->claim->save();
    $this->claim->transitionTo(new ApprovedState($this->claim));
}
🛡️ 3. Security: Race Conditions & IDOR ClaimPolicy.php & ClaimController.php:65
❓ Tutor Question: "What security threat could happen and how do you stop it?"
"Two NGOs clicking 'Claim' at the exact same millisecond for the last food item (Race Condition / Double Claiming), or altering URL IDs to cancel other claims (IDOR)."
💬 Say This (Super Simple):
• Defense 1 (Race Condition): We wrap claim creation inside a database transaction with pessimistic row locking (lockForUpdate()). The database locks the food row until the claim finishes.
• Defense 2 (IDOR / BOLA): We enforce ClaimPolicy. Only the food donor can approve, and only the claiming NGO can assign transport. Others get 403 Forbidden. 
// app/Http/Controllers/ClaimController.php
DB::transaction(function () use ($donation) {
    // Pessimistic row lock prevents double-claiming race condition
    $locked = Donation::where('id', $donation->id)->lockForUpdate()->first();
});

🏗️ 2. Design Pattern: Strategy Pattern Strategies/Notification/NotificationDispatcher.php:20
❓ Tutor Question: "Why did you use Strategy pattern and how does it work?"
"When food batches are near expiration, the system dispatches alerts. Users choose between Email or SMS. The Strategy pattern lets us swap delivery channels at runtime."
💬 Say This (Super Simple):
• NotificationStrategyInterface defines the send contract. EmailStrategy and SMSStrategy implement it.
• NotificationDispatcher selects the strategy based on user preference.
• Why use it (Open/Closed Principle): We can add WhatsApp or Telegram notifications anytime by creating a new strategy class without changing the core inventory code! 
// app/Strategies/Notification/NotificationDispatcher.php
public function dispatch(User $user, string $subject, string $msg): bool {
    $strategy = $this->resolveStrategy($user->notification_preference);
    return $strategy->send($user->email, $subject, $msg);
}
🛡️ 3. Security: Audit Log Tampering (OWASP A09) app/Models/SystemLog.php:20
❓ Tutor Question: "What security threat could happen and how do you stop it?"
"A rogue worker distributes spoiled or expired food and then attempts to alter or delete database logs to avoid legal accountability (Non-Repudiation failure)."
💬 Say This (Super Simple):
• Append-Only Logs: In SystemLog, there are zero update or delete routes in the entire application. Once written, logs can never be altered.
• Audit Attribution: Every entry automatically binds the authenticated user_id, exact timestamp, IP address, and operation.
• Access Restriction: Log views are restricted to Admin role only via middleware. 
// app/Models/SystemLog.php (Append-only audit trail)
SystemLog::create([
    'user_id'     => Auth::id(),
    'action'      => 'inventory.item_logged',
    'description' => "Added batch {batch_no} under safety threshold.",
    'level'       => 'info'
]);
