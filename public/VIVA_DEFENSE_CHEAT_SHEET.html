🏗️ 2. Design Pattern: Observer app/Observers/DonationObserver.php:30
❓ Tutor: "Why did you use Observer pattern and how does it work?"
"We use the Observer Pattern to decouple donation creation from notification delivery. Donation is the Subject; DonationObserver is the Observer."
💬 Say This (Super Simple):
• How it works: When Donation::create() runs, Laravel automatically fires DonationObserver::created().
• The observer dispatches SendDonationNotificationJob to notify the donor and verified NGOs.
• Why use it: Complete decoupling! We can add SMS, WhatsApp, or mobile push alerts in the future without changing a single line of donation code. 
// app/Observers/DonationObserver.php
public function onDonationCreated(Donation $donation): void {
    // Observer triggers background notification job
    SendDonationNotificationJob::dispatch($donation);
}
🛡️ 3. Security: Mass Assignment & BOLA Requests/StoreDonationRequest.php:25
❓ Tutor: "What security threat could happen and how do you stop it?"
"Attackers attempt Mass Assignment (injecting status=claimed to steal food) or Broken Object Authorization (editing someone else's donation ID)."
💬 Say This (Super Simple):
• Mass Assignment Defense: Form Request (StoreDonationRequest) and Model $fillable whitelist. Any unauthorized injected fields are silently stripped out.
• BOLA / IDOR Defense: DonationPolicy checks $user->id === $donation->user_id on update/delete. Unauthorized requests receive an instant 403 Forbidden! 
// app/Policies/DonationPolicy.php
public function update(User $user, Donation $donation): bool {
    return $user->id === $donation->user_id; // 403 Forbidden if not owner
}

🏗️ 2. Design Pattern: Factory Method Services/UserFactory/UserCreator.php:15
❓ Tutor: "Why did you use Factory Method and how does it work?"
"Instead of messy if/else statements during user registration, we use the Factory Method to instantiate specific user roles with their own onboarding policies."
💬 Say This (Super Simple):
• UserCreator is the base factory. Subclasses NgoCreator and DonorCreator instantiate the user.
• How it works: When an NGO registers, NgoCreator automatically sets verification_status = 'pending'.
• When a Donor registers, DonorCreator sets verification_status = 'approved' so they can publish food right away! 
// app/Services/UserFactory/NgoCreator.php
class NgoCreator extends UserCreator {
    protected function makeUser(array $data): User {
        $data['role'] = 'ngo';
        $data['verification_status'] = 'pending'; // Requires admin audit
        return User::create($data);
    }
}
🛡️ 3. Security: Malicious File Upload & RCE VerificationController.php:35
❓ Tutor: "What security threat could happen and how do you stop it?"
"A malicious user tries to upload a .php web shell script disguised as a PDF certificate to achieve Remote Code Execution (RCE) on our server."
💬 Say This (Super Simple):
• Strict MIME Validation: We enforce mimes:pdf,jpg,png|max:5120. PHP and executable files are immediately rejected.
• Hashed Filenames: Files are renamed to random SHA-256 hashes so original filenames cannot be targeted.
• Private Disk Storage: Files are stored in Storage::disk('private') outside the public web root, completely preventing direct execution! 
// app/Http/Controllers/VerificationController.php
$request->validate([
    'document' => 'required|file|mimes:pdf,jpg,png|max:5120',
]);
$path = $request->file('document')->store('verification_docs', 'private');

🏗️ 2. Design Pattern: State Pattern States/Claim/ClaimState.php:18
❓ Tutor: "Why did you use State pattern and how does it work?"
"Claims transition through strict stages: Pending ➔ Approved ➔ Collected. Each status is its own class instead of messy switch/case code."
💬 Say This (Super Simple):
• ClaimState is the base class. Concrete classes are PendingState, ApprovedState, and CollectedState.
• How it works: In PendingState, you can only approve() or reject().
• Why use it: Prevents illegal transitions! You cannot call collect() on a pending claim—the state class blocks it automatically! 
// app/States/Claim/PendingState.php
public function approve(): void {
    $this->claim->status = 'approved';
    $this->claim->save();
    $this->claim->transitionTo(new ApprovedState($this->claim));
}
🛡️ 3. Security: Race Conditions & IDOR ClaimPolicy.php & ClaimController.php:65
❓ Tutor: "What security threat could happen and how do you stop it?"
"Two NGOs clicking 'Claim' at the exact same millisecond for the last food item (Race Condition / Double Claiming), or altering URL IDs to cancel other claims (IDOR)."
💬 Say This (Super Simple):
• Pessimistic Row Lock: We wrap claim creation in DB::transaction() with lockForUpdate(). The row is locked until finished, preventing double claiming.
• IDOR Protection: ClaimPolicy verifies only the owning donor can approve, and only the claiming NGO can assign vehicles. 
// app/Http/Controllers/ClaimController.php
DB::transaction(function () use ($donation) {
    // Pessimistic row lock prevents double-claiming race condition
    $locked = Donation::where('id', $donation->id)->lockForUpdate()->first();
});

🏗️ 2. Design Pattern: Strategy Pattern Strategies/Notification/NotificationDispatcher.php:20
❓ Tutor: "Why did you use Strategy pattern and how does it work?"
"When food batches near expiration, the system alerts staff. Users choose between Email or SMS. Strategy pattern allows swapping delivery channels dynamically."
💬 Say This (Super Simple):
• NotificationStrategyInterface defines the send method. EmailStrategy and SMSStrategy implement it.
• NotificationDispatcher selects the strategy based on user preference.
• Why use it: Open/Closed Principle! We can add WhatsApp or Telegram notifications anytime by creating a new class without modifying existing code. 
// app/Strategies/Notification/NotificationDispatcher.php
public function dispatch(User $user, string $subject, string $msg): bool {
    $strategy = $this->resolveStrategy($user->notification_preference);
    return $strategy->send($user->email, $subject, $msg);
}
🛡️ 3. Security: Audit Log Tampering (OWASP A09) app/Models/SystemLog.php:20
❓ Tutor: "What security threat could happen and how do you stop it?"
"A corrupt worker distributes spoiled food and then attempts to alter or delete database logs to escape blame (Non-Repudiation failure)."
💬 Say This (Super Simple):
• Append-Only Logs: In SystemLog, there are zero update or delete routes in the entire application. Once written, logs cannot be modified.
• Audit Attribution: Every entry automatically binds the authenticated user_id, exact timestamp, IP address, and operation.
• Access Restriction: Log views are restricted to Admin role only via middleware. 
// app/Models/SystemLog.php (Append-only audit trail)
SystemLog::create([
    'user_id'     => Auth::id(),
    'action'      => 'inventory.item_logged',
    'description' => "Added batch {batch_no} under safety threshold.",
    'level'       => 'info'
]);
